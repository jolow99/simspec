# Environment / benchmark frameworks vs. the (i)+(ii)+(iii) claim

Research date: 2026-10-16. Claim under test: *no existing framework offers together*
(i) ENFORCED observation structure (agents cannot read state they are not declared to observe),
(ii) first-class Rules (contracts/norms with compliance checks),
(iii) rational, non-LLM, exact-inference baseline agents,
plus (iv) a standard trajectory log.

Method: full text of the three arXiv papers (PDF -> `pdftotext -layout`, all v1, no later versions
exist as of today), plus the official source repositories cloned at HEAD (and Concordia at tag
`v1.8.9`, the contest release named in the paper). All quotes are verbatim; file paths are to the
cloned sources under
`(local scratch, not committed)`.

Legend used below for "observation enforcement":
- **by construction** = the only interface through which an agent can get information is one that
  is partitioned per player, and the agent object never receives a handle to the full state;
- **by convention** = the API *names* a per-player observation, but agent code holds a reference
  (env object, state object, shared dict) from which the full state is reachable.

## 1. Concordia Contest paper (arXiv 2512.03318, NeurIPS 2025 D&B) + Concordia v1.8.9 code

### What it standardizes
- An evaluation **protocol**, not an execution engine: "we separate scenarios into a substrate—the
  component capturing the rules and dynamics that govern the environment in which the agents
  interact—from the background population of agents embedded in it." (§3.1)
- Formal model: "we model a substrate as an n-player Partially-Observable Stochastic Game without
  Rewards (POSG\R), that we denote by E = ⟨S, O, A, p⟩ … a joint observation space
  O = O1 × O2 × … On" (§3.1). This is a *paper-level* formalization; the code has no typed
  observation spaces (observations are free-text strings, see below).
- Focal vs background and resident vs visitor: "resident scenarios G_R = ⟨E, ρ, resident⟩ … a
  majority of agents playing π and a minority playing ρ" / "visitor scenarios G_V = ⟨E, ρ, visitor⟩
  … a majority of agents playing ρ and a minority agent playing π" (§3.1).
  Code: `ScenarioConfig(description, substrate_config, background_agent_module,
  time_and_place_module, focal_is_resident, tags)` in
  `concordia189/examples/modular/scenario/scenarios.py`.
- Held-out evaluation: "a development phase, where participants submitted focal agents for
  evaluation against a set of publicly available scenarios … and an evaluation phase where the
  submitted agents were assessed on a set of held-out scenarios" (§4.1); "the 14 held-out scenarios
  cover only a slice" (§7).
- Agent contract: "π ≡ LLM(f(o)) … Participants were only required to submit scaffolding
  functions." (§4.2). The submitted `build_agent(config, model, memory, clock)` factory
  (`concordia189/concordia/factory/agent/rational_agent.py` signature) never receives the game
  master.
- Single LLM for all entrants: Gemma-2-9b-it; "strict limitation on the number of … LLM calls an
  agent can make per step" (§9.2.1).

### How scores are computed
- "Each environment was equipped with a language model-based reward model that assigned
  quantitative scores to agents based on the outcomes generated by the game master (GM), with
  scoring being highly contextual to each environment." (§9.2)
- Code: per-substrate payoff components, e.g. `CoordinationPayoffs` in
  `concordia189/examples/modular/environment/pub_coordination.py` (`return_payoffs_sum()` sums
  `payoff.get_scores()`); outcome returned as
  `SimulationOutcome(resident_scores, visitor_scores, metadata)`
  (`examples/modular/utils/logging_types.py`).
- Aggregation: "Raw scores were first rescaled to the [0, 1] interval with a per-scenario min–max
  normalization based on scenario theoretical minimum and maximum." (§5); ranking by Elo plus
  "Iterative Maximal Lotteries, Copeland, and Ranked Pairs" implemented "via OpenSpiel [33]"
  (§9.3). `launch_concordia_challenge_evaluation.py` computes
  `focal_per_capita_score = np.mean(focal_scores)` etc. (lines 268-283).

### Assumptions
- Mixed-motive, "cooperation-eliciting" text scenarios; turn-taking mediated by an LLM game master
  ("every agent interacts with the environment via natural-language observations and action
  intents, all mediated by a Game Master which resolves those intents into world events", §9.2).
- Untyped: actions are "unstructured natural language outputs" (§9.2); `Entity.act()` "will
  always be a string" and `observe(observation: str)` "Always a string"
  (`concordia189/concordia/typing/entity.py`).

### Observation enforcement
- Mechanism: GM pushes strings. `GameMaster._step_player`:
  `for observation in self._player_observations(player.name): player.observe(observation)`,
  where `_player_observations` iterates `comp.partial_state(player_name)` over GM components
  (`concordia189/concordia/environment/game_master.py` lines 278-305). After an action,
  `if self._player_observes_event: self._players_by_name[player_name].observe(event_statement)`.
- Verdict: **by construction at the API boundary, but not declared or typed.** The agent object
  is constructed without a reference to the GM or its memory, so it can only see what the GM
  `observe()`s to it. However *what* each player sees is decided at run time by each GM
  component's `partial_state()` (often LLM-generated prose) — there is no declarative per-player
  observation schema that could be statically checked. The paper's "O = O1 × … × On" exists only
  in the paper. The "veil of ignorance" (§4.1) is about hiding *scenario identity* from the
  designer, not an observation-restriction mechanism.

### First-class rules / norms
- None as objects. Scenario tags like "Convention Following: Scenarios where agents are
  encouraged to adopt and adhere to shared social norms, rules, or coordination patterns that
  emerge through interaction." (Table 13) are *annotations* for post-hoc Bayesian analysis, not
  checkable rules. GM components in v1.8.9 (`components/game_master/`: `coordination_payoffs.py`,
  `schelling_diagram_payoffs.py`, `inventory_based_score.py`, `player_status.py`, `schedule.py`,
  `triggered_function.py`…) encode payoffs/dynamics, not contracts with compliance checks.
  Current main adds `payoff_matrix.py`, `world_state.py`, `scene_tracker.py`, `terminate.py` —
  still no rule/contract/compliance abstraction (grep for `Rule|Norm|Contract|compliance` classes:
  none). Rule-following is judged implicitly by the LLM GM when it resolves "attempted action"
  into an "event statement" (`_handle_action`).

### Rational baselines
- The paper's "rational agent baseline" (§5, Fig. 2; `rational_agent` rows in Tables 3-12) is
  **an LLM agent**, not exact inference: `concordia189/concordia/factory/agent/rational_agent.py`
  `build_agent(*, config, model: language_model.LanguageModel, memory, clock, …)` wires LLM
  components (`ObservationSummary(model=model, …)`). The current prefab says it explicitly: "A
  prefab for a 'rational' agent (logic of consequence). … rational: situation -> available
  options -> 'which option is best?'" with every perception component taking `model=model`
  (`concordia/concordia/prefabs/entity/rational.py`).
- Puppets: `basic_puppet_agent` (supporting agents "being stubborn and always choosing their
  preference", `scenarios.py`); current `prefabs/entity/puppet.py`: "responds with pre-configured
  fixed responses for specific calls to action. If no fixed response matches, it falls back to
  generating a response using the language model." These are scripted, not game-theoretic.
- Rational/solver baselines: **none** (no CFR/MCTS/best-response in the repo).

### Log format
- Per run: "writes an html file with its full text log … `SCENARIO_NAME__YYYY-MM-DD HH:MM:SS.html`"
  and a JSON list of `ScenarioResult` dataclasses (`focal_per_capita_score`,
  `background_per_capita_score`, `ungrouped_per_capita_score`, `simulation_outcome`,
  `focal_is_resident`, `model`, `embedder`, `exclude_from_elo_calculation`, …)
  (`launch_concordia_challenge_evaluation.py` docstring; `logging_types.py`).
- Step-level: `GameMaster._log.append(update_log)` with keys `'Event statement'`, `'Chain of
  thought'`, `'Active player': {'Name', 'Action attempt', 'Context for action selection and
  components'}` — a list of nested dicts, rendered to HTML; **no schema file, no typed trajectory
  format**. Participants complained of "incomplete log outputs" (§9.5.5).

### Adapter from a typed spec
- Cheap: scenario registry (`ScenarioConfig`), focal/background slot assignment, resident/visitor
  modes, score aggregation and Elo/VasE — all table-driven.
- Hard: the GM is an LLM; a typed state would have to be *narrated* into strings for `observe()`
  and parsed back out of free-text actions; rule compliance would have to be re-implemented as GM
  components; the per-player observation partition would be enforced only as far as the adapter's
  own `partial_state()` code is correct.

**Verdict for item 1:** (i) partial (API boundary only, not declared/typed); (ii) absent;
(iii) absent (the "rational" baseline is an LLM). Claim **not refuted**.

## 2. MultiAgentBench / MARBLE (arXiv 2503.01935; github.com/ulab-uiuc/MARBLE)

### What it standardizes
- A coordination framework + six scenarios: "the Coordination Engine, responsible for initializing
  and synchronizing key modules—including the Agent Graph, Cognitive Module, and Coordinate Engine"
  (§3.1); "four distinct coordination protocols … star, tree, graph, and chain" (§3.1.1).
- Agent graph: "a structured graph G = (A, E) … each edge in E is defined as a triple (a_i, r, a_j)
  with r ∈ R representing the relationship … we ensure that subsequent communication and
  coordination occur exclusively between agents with explicitly defined relationships" (§3.1).
  Code: `AgentGraph.__init__` reads `structure_config.relationships` triples
  (`marble/marble/graph/agent_graph.py`); `BaseAgent.act` builds the `new_communication_session`
  tool whose `target_agent_id` enum is `list(self.relationships.keys())`
  (`marble/marble/agent/base_agent.py` lines 169-195). **The communication graph is enforced by
  tool-schema construction** — the only genuinely enforced structure in MARBLE.
- Metrics: "KPI_overall = (1/N) Σ KPI_j = (1/(NM)) Σ n_j" (milestone detection by an LLM);
  "Communication Score (C_score) is derived from an LLM-based evaluation … on a five-point scale";
  Planning Score likewise; "Coordination Score (CS) is then computed by averaging these two
  sub-scores" (§3.3). Prompts are reproduced verbatim in Figs. 22-25.

### Assumptions
- LLM agents with function calling ("MARBLE framework required function-calling abilities", §4.1);
  mostly cooperative task completion; Werewolf and Bargaining are the "Agents with Conflicting
  Goals" scenarios (§3.2). Untyped: environment state is `self.state: Dict[str, Any]`
  (`marble/marble/environments/base_env.py`).

### Observation enforcement
- Generic path: `BaseAgent.perceive(state)` returns `state.get("task_description", "")`, and
  `BaseEnvironment.get_state()` returns `self.state.copy()` — the full state is available to any
  caller. `act()` prompts with task + memory + other agents' profiles; no per-agent observation
  spec exists.
- Werewolf (the hidden-information scenario): the paper says "This environment adheres to a
  strict, environment-mediated communication protocol … all messages pass through the environment
  … prevents unauthorized agent-to-agent exchanges" (§A.5.3). But the code gives every agent the
  whole shared dictionary: `WerewolfAgent.__init__(…, shared_memory: Dict[str, Any], …)` with
  `self.shared_memory = shared_memory`, and the environment stores
  `self.shared_memory["private_state"]["players"][agent_id] = {"role": role, "status": status,
  "personal_event_log": …}` for **all** players (`werewolf_env.py` lines 191-195). The agent code
  reads `self.shared_memory["private_state"]["players"][self.agent_id]` (werewolf_agent.py line
  303, 576) — restricting itself to its own entry **by convention**; nothing prevents indexing
  another player's `"role"`.
- Verdict: **by convention only**; no declared observation structure.

### First-class rules
- None. Werewolf phase/vote logic is hard-coded in `werewolf_env.py` ("The environment enforces
  the standard Werewolf game flow", §A.5.3); scoring is a hand-written points table (Table 3).
  No rule/norm/contract/compliance class anywhere in `marble/` (grep: none). Relationship triples
  (`collaborates`, `supervises`, `negotiates`) are labels, not contracts with checks.

### Rational baselines
- None. All agents are LLMs; the Werewolf "baseline" is "gpt-4o(baseline)" (Table 5) and
  "the werewolf side remains consistently powered by GPT-4o" (§A.5.2).

### Log format
- `Engine._write_to_jsonl` appends `json.dumps(summary_data)` to
  `result/discussion_output.jsonl` (engine.py 1090-1108); contents are per-iteration dicts with
  `communications`, scores and summaries — not a per-step trajectory schema. Werewolf dumps the
  whole `shared_memory` JSON repeatedly (`json.dump(self.shared_memory, f, indent=4)`) and keeps
  `public_event_log` / `private_event_log` / per-player `personal_event_log` strings
  (`log_event`, lines 1020-1080). Python `logging` to stdout otherwise (`utils/logger.py`).
  The paper: "Each agent's private event log and final decisions are stored, allowing for
  reproducibility and subsequent scoring" (§A.5.3) — free text, no schema.

### Adapter from a typed spec
- Cheap: register typed actions as OpenAI-format tools via `BaseEnvironment.register_action`;
  map the spec's communication topology onto `relationships` triples (this part would be enforced).
- Hard: observation restriction must be re-implemented in `perceive()` and every scenario agent;
  MARBLE's evaluator is LLM-judge-based, so rule compliance would need a parallel evaluator; no
  seat for a non-LLM agent (agents must emit function calls through `model_prompting`).

**Verdict for item 2:** (i) absent (convention; hidden-role data is reachable); (ii) absent;
(iii) absent. Claim **not refuted**.

## 3. CoGrid & Multi-User Gymnasium (arXiv 2604.15044; github.com/chasemcd/cogrid, github.com/chasemcd/mug)

### What it standardizes
- CoGrid: PettingZoo-Parallel grid-worlds with pluggable components. "All CoGrid environments are
  partially observable Markov decision processes (POMDPs), described by the tuple (X, A, O, T, R,
  Ω)" (§3). `class CoGridEnv(pettingzoo.ParallelEnv)` (`cogrid/cogrid/cogrid_env.py` line 27).
- Observations: "Environments specify features by name in a configuration file. Each Feature
  subclass provides a pure function that maps the current state to an observation vector … composed
  into a single observation for each agent" (§3). Docs: "Per-agent features are computed once for
  each agent and arranged in ego-centric order: 1. Focal agent's features 2. Other agents'
  features … Global features are appended once, identically for all agents."
  (`cogrid/docs/concepts/observations.md`). Code:
  `get_all_agent_obs(feature_fn, state, agent_ids)` returns `{aid: feature_fn(state, i) …}`
  (`cogrid/cogrid/feature_space/features.py` line 200).
- Rewards: declarative `InteractionReward` subclasses (`action = "pickup_drop"; holds =
  "onion_soup"; faces = "delivery_zone"`, Listing 2).
- Object capabilities: `when()` descriptor — "Declarative capability descriptor for grid objects …
  `can_pickup_from = when(agent_holding="plate")`" with `SUPPORTED_CONDITIONS = frozenset({"agent_holding"})`
  (`cogrid/cogrid/core/objects/when.py`).
- MUG: experiment flow (`Stager` of `Scene`s, `GymScene`), Pyodide client execution, GGPO rollback
  ("environments must be deterministic given a random seed and must implement … get_state() and
  set_state()", §4).

### Assumptions
- Simultaneous-move (Parallel API), numeric Box/Discrete spaces, cooperative *or* competitive
  grid tasks; human-AI focus. "The primary goal is to provide a platform that can be easily
  manipulated … rather than serving as a platform for standardized benchmarks." (§2)
- "MUG does not currently support explicit communication between participants or between humans
  and AI. All interaction is implicit" (§6).

### Observation enforcement
- Per-agent observation vectors are produced by the env and returned from `step()` as a dict
  keyed by agent id (`cogrid_env.py` 473-530). But (a) the policy sits outside the env and can call
  `env.get_state()` ("Restorable via set_state"), and (b) feature lists freely include global
  features (`object_type_masks`, `environment_layout`, `order_observation` are "Per-Agent: No").
  Nothing declares what an agent *may not* see.
- Verdict: **by convention** (standard PettingZoo situation). Observation structure is
  declarative (feature list in config), which is a plus, but not restrictive.

### First-class rules
- `when()` guards and `InteractionReward` are **dynamics/reward declarations**, not norms or
  contracts: they define what is physically possible and what pays, not what is permitted with a
  compliance verdict. No rule/norm/contract abstraction in `cogrid/` or `mug/`.

### Rational baselines
- None exact. Paper trains PPO via RLlib ("trained a reinforcement learning policy with … PPO",
  §5); MUG examples ship a heuristic `ball_chaser.py` for Slime Volleyball. No solver/exact
  inference.

### Log format
- MUG: "`{subject_id}_ep{N}.csv` | At the end of every episode of a GymScene | Observations,
  actions, rewards, terminateds, truncateds, episode_num, timestep t — nested dicts flattened with
  dotted column names" plus `{subject_id}_metadata.json`, `_globals.json`,
  `_multiplayer_metrics.json` (`mug/docs/core-concepts/participants-and-data.md`). Paper: "By
  default, all information returned in the infos dictionary from the environment is logged at
  every step" (§4). This is a **concrete per-step CSV trajectory format** — the strongest "(iv)"
  among the LLM-adjacent items — but it is experiment-platform output, not a spec-level schema.
- CoGrid itself has no logger.

### Adapter from a typed spec
- Cheap if the spec's state is grid-like: write `Feature` subclasses per declared observation
  field and a `CoGridEnv` subclass; MUG then gives browser play + CSV logs for free.
- Hard: non-grid or text/communication games don't fit ("The primary limitation of CoGrid is the
  grid-based nature", §6; no chat in MUG); rules must become `when()` guards + Python hooks
  (`on_interact`, `on_step`), which cannot express contracts over histories.

**Verdict for item 3:** (i) convention; (ii) absent (dynamics guards ≠ norms); (iii) absent
(PPO/heuristics). Claim **not refuted**.

## 4a. PettingZoo (pettingzoo.farama.org; AEC + Parallel)

### What it standardizes
- Two loop APIs. AEC: "agents act sequentially, receiving updated observations and rewards before
  taking an action … flexible enough to handle any type of game that multi-agent RL can consider"
  (`docs/api/aec.md`). Parallel: "a secondary parallel API for environments where all agents have
  simultaneous actions and observations … based around the paradigm of Partially Observable
  Stochastic Games (POSGs)" (`docs/api/parallel.md`).
- Typed per-agent spaces: `observation_spaces`/`action_spaces`: "A dict of the observation spaces
  of every agent, keyed by name" (Gymnasium spaces: Box, Discrete, Dict, Text, …); action masks
  "optional, and can be implemented using either observation or info".

### Assumptions
- Agnostic as to competitive/cooperative/mixed; agents are opaque policies; no rules of a game are
  represented beyond `step()` semantics and (optionally) a mask.

### Observation enforcement
- `AECEnv.observe(agent)`: "Returns the observation an agent currently can make. `last()` calls
  this function." And `state()`: "State returns a global view of the environment. It is
  appropriate for centralized training decentralized execution methods like QMIX"
  (`pettingzoo/pettingzoo/utils/env.py` lines 86-112, 374-384).
- Verdict: **by convention**. The training loop holds `env`; `env.observe(other)`, `env.state()`
  and every env attribute are reachable. The API documents *a* per-agent observation, it does not
  prevent reading others'.

### First-class rules: none (legal-action masks only).
### Rational baselines: none shipped. Tutorials are `agilerl, cleanrl, custom_environment,
langchain, rllib, sb3, tianshou` (`docs/tutorials/`), i.e. learning libraries.
### Log format: none standardized.

### Adapter from a typed spec
- Cheap mechanically (typed spaces map 1:1 to `gymnasium.spaces`; AEC covers turn-based,
  Parallel covers simultaneous); but the adapter must itself implement observation partitioning,
  rules and logging — PettingZoo adds nothing for (i)-(iv) beyond the loop contract.

**Verdict 4a:** (i) convention; (ii) none; (iii) none. Claim **not refuted**.

## 4b. OpenSpiel (openspiel.readthedocs.io; spiel.h)

### What it standardizes
- Extensive-form game tree: "A `Game` object contains the high level description for a game (e.g.
  whether it is simultaneous or sequential, the number of players, the maximum and minimum scores).
  A `State`, which describes a specific point … within a trajectory." Chance is "an explicit player
  (the 'chance' player, which has id kChancePlayerId)" (`docs/concepts.md`).
- Typed meta-information per game (`GameType` in `open_spiel/spiel.h`): `dynamics`
  (SEQUENTIAL/SIMULTANEOUS), `chance_mode`, `information` (PERFECT/IMPERFECT), `utility`
  (ZERO_SUM/…), `reward_model`, and booleans `provides_information_state_string/tensor`,
  `provides_observation_string/tensor` (spiel.h lines 130-138).
- Per-player information state is **formally specified**: "For imperfect information games.
  Returns an identifier for the current information state for the specified player. Different
  ground states can yield the same information state for a player when the only part of the state
  that differs is not observable by that player (e.g. opponents' cards in Poker.) … The information
  state should be perfect-recall" (spiel.h ~589-617). `information_state_string(player)`,
  `information_state_tensor(player)`, `observation_string(player)`, `observation_tensor(player)`
  (docs/api_reference). Kuhn example: "InformationStateString(0) = '0pb'",
  "InformationStateString(1) = '1pb'".
- Legality is enforced: `apply_action_with_legality_check`, `legal_actions_mask`.

### Assumptions
- Game-theoretic: finite discrete actions, terminal/per-step rewards, tree-structured; natural
  language only via custom games/string actions. Competitive, cooperative or general-sum all
  supported (`Utility` enum).

### Observation enforcement
- Verdict: **declared and formal, but not enforced against the agent.** The agent receives the
  full `State` object (e.g. `bot.step(state)`); it may call `state.information_state_string(p)`
  for any `p` or `state.history()`. The framework's guarantee is that the *information structure
  is well-defined and algorithm-consumable* (so CFR/exploitability are correct), not that a policy
  cannot cheat. OpenSpiel is the only item where (i) is at least *declared* as a typed,
  per-player, perfect-recall object.

### First-class rules
- Rules = the game implementation (legal actions, transitions, returns). No norms/contracts layer;
  no compliance-check abstraction beyond legality.

### Rational baselines — the strongest in this set
- `docs/algorithms.md` (thoroughly-tested entries marked green): "Counterfactual Regret
  Minimization (CFR)", "CFR-BR", "Exploitability / Best response", "External sampling Monte Carlo
  CFR", "Outcome sampling Monte Carlo CFR", "Monte Carlo Tree Search", "Minimax (and Alpha-Beta)
  Search", "Sequence-form linear programming", "Lemke-Howson (via nashpy)", "Value Iteration",
  "Policy Iteration", "α-Rank", "Voting-as-Evaluation (VasE)". Python modules:
  `open_spiel/python/algorithms/{cfr.py, cfr_br.py, exploitability.py, best_response.py,
  external_sampling_mccfr.py, outcome_sampling_mccfr.py, mcts.py, ismcts.py, minimax.py,
  lp_solver.py, matrix_nash.py, mip_nash.py, nash_averaging.py}`.
  These are exact/tabular, non-LLM, exact-inference baselines — satisfying (iii) on its own.

### Log format
- Standard **playthrough** text format, 181 files under
  `open_spiel/integration_tests/playthroughs/*.txt`: header dumps `GameType.*`, tensor shapes,
  then for each state `IsTerminal() … History() … CurrentPlayer() … InformationStateString(p)
  … ObservationString(p) … PublicObservationString() … PrivateObservationString(p) …
  LegalActions()` followed by `# Apply action "Deal:1" / action: 1`. Also `state.serialize()`,
  `state.history()`, `serialize_game_and_state`. This is a de-facto standard trajectory log with
  per-player information states at every node — satisfying (iv) for discrete games.

### Adapter from a typed spec
- Moderate: implement a Python/C++ game (`new_initial_state`, `legal_actions`, `apply_action`,
  `information_state_string(player)`, `returns`). Observation partition must be hand-written per
  game but then every solver/evaluation works. Hard for free-text or large/continuous action spaces
  (information states must be enumerable for tabular solvers); no place for rules/norms except
  by encoding them as legality or utility.

**Verdict 4b:** (i) declared/typed but **not enforced against agent code** (convention at the
agent boundary); (ii) none; (iii) **yes**; (iv) yes. Claim **not refuted** (fails (i) and (ii)),
but OpenSpiel is the closest prior art for (iii)+(iv) and for *declaring* (i).

## 4c. Melting Pot (github.com/google-deepmind/meltingpot)

### What it standardizes
- Substrates/scenarios/background bots: "over 50 multi-agent reinforcement learning substrates …
  and over 256 unique test scenarios … performance of agents on these held-out test scenarios
  quantifies whether agents: perform well across a range of social situations … interact
  effectively with unfamiliar individuals not seen during training" (README).
- `ScenarioConfig(description, tags, substrate, roles, is_focal, bots_by_role)` with e.g.
  `is_focal=(True,)*4 + (False,)*12` (`meltingpot/configs/scenarios/__init__.py`).
- Policy interface: `Policy.initial_state()`, `Policy.step(timestep: dm_env.TimeStep, prev_state)
  -> (action, next_state)`, "Must not possess any mutable state not in `initial_state`"
  (`meltingpot/utils/policies/policy.py`).
- Per-player specs: `specs.OBSERVATION = {'READY_TO_SHOOT', 'RGB' (88,88,3), 'POSITION',
  'ORIENTATION'}` (`meltingpot/utils/substrates/specs.py`); substrate `observation_spec()` returns
  `Sequence[Mapping[str, dm_env.specs.Array]]` (one mapping per player).
- Substrate config distinguishes `individual_observation_names = ["RGB", "READY_TO_SHOOT", …]`
  from `global_observation_names = ["WORLD.RGB"]` with the comment "Debug only (do not use the
  following observations in policies)" (`configs/substrates/clean_up.py` 813-833).

### Assumptions
- Simultaneous-move gridworld (DMLab2D, Lua components), pixel observations, mixed-motive social
  dilemmas; evaluation separates focal from background. Rules of a substrate live in Lua
  `Component`s (`docs/concepts.md`).

### Observation enforcement — the only *mechanically enforced* restriction found
- `Scenario` strips observations before they reach focal agents:
  `_restrict_observation(observation, permitted_observations)` keeps only keys in
  `PERMITTED_OBSERVATIONS = frozenset({'RGB', 'HUNGER', 'INVENTORY', 'MY_OFFER', 'OFFERS',
  'READY_TO_SHOOT', 'STAMINA', 'VOTING', 'COLLECTIVE_REWARD'})` (`meltingpot/scenario.py` 47-59);
  `Scenario._split_timestep` partitions by `is_focal` and applies `_restrict_observations` to the
  focal half; `observation_spec()` is likewise restricted (`utils/scenarios/scenario.py`
  101-240). Docstring: "If applied [substrate_transform], the observations will not be restricted
  to PERMITTED_OBSERVATIONS … intended for training purposes and should not be used during
  evaluation."
- Verdict: **by construction for the evaluation harness** (the Scenario wrapper's public
  `step()/reset()/observation()/observation_spec()` never expose `WORLD.RGB` or background
  players' observations). Caveat: it is still Python (`scenario._substrate` is reachable), and
  the restriction is a global allow-list of *keys*, not a per-player declaration in a spec — all
  focal players get the same key set. It is enforcement of a fixed convention, not of a
  user-declared observation structure.

### First-class rules
- None. Dynamics/sanctioning are Lua components (e.g. `Zapper`); scenario `tags` (e.g.
  `'convention_following'`) are annotations. No contract/norm object with compliance checks.

### Rational baselines
- Background "bots" are **learned saved models**, optionally steered by hand-coded **puppeteers**:
  `bot.build_from_config` loads `SavedModelPolicy(config.model_path)` and, if configured, wraps it
  in `PuppetPolicy(puppeteer=…, puppet=saved_model)` (`meltingpot/bot.py` 50-69). "A puppeteer
  that controls the timestep forwarded to the puppet" by injecting a `GOAL` one-hot
  (`utils/puppeteers/puppeteer.py`), e.g. goals `'CONSUME_ANY','PREFER_RED','FREERIDE_RED',
  'ZAP_OTHERS'` (`configs/bots/__init__.py`). These are scripted/learned, **not exact-inference
  rational agents**. No solver.

### Log format
- `utils/evaluation/evaluation.py`: `run_and_observe_episodes` subscribes to focal/background
  `timestep` observables, accumulates `focal_player_returns`, `background_player_returns` into a
  `pandas` DataFrame, optional `VideoSubject` to write videos. Observables (`ScenarioObservables`:
  `action`, `timestep`, `events`, `background`) allow custom logging, but there is **no standard
  trajectory file format** (returns table + video only).

### Adapter from a typed spec
- Hard: substrates must be authored in Lua components + Python config on DMLab2D; observations are
  pixel-centric; text/communication games do not fit. Focal/background slotting and the
  permitted-key restriction are reusable patterns, not a reusable engine for a typed spec.

**Verdict 4c:** (i) partially by construction (fixed key allow-list in the Scenario wrapper, not
a declared per-player structure); (ii) none; (iii) none (learned puppets + scripted puppeteers).
Claim **not refuted**.

## Summary (≈300 words)

The project lead's claim survives every item examined, but with important nuance. None of the six
frameworks provides, together, (i) enforced and declared per-agent observation structure, (ii)
first-class rules with compliance checks, and (iii) non-LLM exact-inference rational baselines.

The LLM-oriented items are weakest. The **Concordia Contest** standardizes a *protocol*
(substrate vs background population, resident vs visitor, held-out scenarios, Elo/VasE ranking)
and formalizes substrates as POSG\R on paper, but in code observations are free-text strings pushed
by an LLM game master via `partial_state(player_name)`; there is no typed observation schema, no
rule objects, and its "rational agent" baseline is itself an LLM. **MARBLE** enforces only the
communication graph (via tool-schema enums); its hidden-role Werewolf agents receive the entire
`shared_memory` including every player's role, so observation restriction is purely by convention,
and all baselines are LLMs. **CoGrid/MUG** sits on PettingZoo: observation features are
declaratively listed but global features and `get_state()` are open to policies; `when()` guards
and `InteractionReward` are dynamics, not norms; baselines are PPO/heuristics. MUG does ship a
concrete per-episode CSV trajectory log.

The MARL/game-theory items each supply a different piece. **PettingZoo** supplies typed per-agent
spaces and two loop APIs but nothing for (i)-(iv). **OpenSpiel** is the strongest prior art:
information states are formally declared per player with perfect-recall semantics, exact
rational baselines (CFR, MCCFR, best response/exploitability, MCTS, minimax, LP/Nash solvers)
satisfy (iii) outright, and its playthrough format is a de-facto standard log — yet agents hold
the full `State` and there is no norm/contract layer. **Melting Pot** is the only system that
mechanically strips observations (fixed `PERMITTED_OBSERVATIONS`, focal/background partition in
`Scenario`), but the allow-list is global, not spec-declared, and its "bots" are learned models
steered by scripted puppeteers, not rational solvers.

Verdicts: item 1 not refuted; item 2 not refuted; item 3 not refuted; PettingZoo, OpenSpiel,
Melting Pot each not refuted. The honest framing for the paper: OpenSpiel already offers (iii)+(iv)
and *declares* (i); Melting Pot *enforces* a fixed version of (i); no framework offers (ii), and
none combines (i)+(ii)+(iii) for LLM agents.
