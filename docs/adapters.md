# Adapters and exporters

The core is standalone. These adapters show what interop costs; only the first two are runnable.

| Target | What exists | Cost | What is lost |
|---|---|---|---|
| **PettingZoo** (`simspec/adapters/pettingzoo_env.py`) | A `ParallelEnv`-shaped wrapper: `reset(seed) -> (obs, infos)`, `step({agent: action}) -> (obs, rewards, terminations, truncations, infos)`, `possible_agents`, per-agent `action_mask`. Drives the real engine, so rules, chance logging and the card still work. Tested with the norms game (`tests/test_adapters.py`). | Cheap (about 100 lines). | Only single simultaneous-phase games with finite choice actions; observations are dicts, not `gymnasium.Space`s (add a `Dict` space builder from the schema if a trainer needs it); sequential/protocol phases would need the AEC API. |
| **Inspect AI log export** (`simspec/export/inspect_log.py`) | Writes an `EvalLog` with one sample per episode, every simspec event as an `InfoEvent`, model calls as info events, the Harness Card in `eval.metadata`. Verified API in `docs/research/experiments/eval_inspect.py`. | Cheap; needs `pip install inspect-ai` only when exporting. | Inspect's viewer shows our events as generic info, not as `ModelEvent`s (mapping each `calls.jsonl` record to a `ModelEvent` needs Inspect's `ChatMessage`/`ModelOutput` types; a few dozen lines, not done). |
| **TextArena** (`simspec/adapters/textarena_env.py`) | A `reset / get_observation / step(str) / close` env over sequential and protocol phases, rendering observations with the game's renderer and parsing action strings with the scaffold's parser. | Cheap for sequential games (about 80 lines); simultaneous phases need the same "collect then resolve" emulation TextArena uses for IPD. | TextArena has no observation structure beyond per-player inboxes and no rules; the enforcement happens only inside our engine, invisible to TextArena agents and to its ladder. |
| **Concordia** | Not built. Design: a Game Master prefab whose `MakeObservation`, `NextActing`, `NextActionSpec`, `EventResolution` and `Terminate` components call `GameSpec.observe / Phase.actors_in / ActionSpec / transition / terminal` with `allow_llm_fallback=False`, plus an `ActionSpec` bridge (`CHOICE` with our keys as options, `FREE` for text slots). | Hard: Concordia's actions and observations are strings and its state lives in text memory, so every typed value has to be rendered and parsed at the boundary, and Concordia's own components (memory, world state, inventory) would duplicate ours. Roughly a day of work for a faithful GM. | Deterministic replay (Concordia has no run seed and threads inside `act`), the vault lock (Concordia hands the GM to the engine, not to players, so observation enforcement survives only by convention), and rule events unless re-logged by the GM component. |
| **OpenSpiel** | Not built. The spec already exposes what OpenSpiel's `Game`/`State` need: `legal_actions(player)` from `ActionSpec.legal_keys`, `information_state_string(player)` from `GameSpec.observe` + renderer, chance via logged draws. | Medium: OpenSpiel's Python `Game` subclassing is well documented; simultaneous phases map to `kSimultaneousPlayerId`. | Nothing essential; this is the most natural export for solver baselines (CFR, best response). |
